# 0.5.0 - Subagent thread continuity (design + probe evidence)

Goal: when revisiting the same work (rework after a review, re-review after a fix), RESUME the same
per-role subagent thread instead of re-dispatching a fresh one, so context is preserved (time/cost,
consistency) - WITHOUT crossing the author<->reviewer independence boundary.

## The one inviolable boundary: continuity is PER-ROLE, never one merged thread

Independence (the fidelity control) = the one who carves is never the one who reviews, on a different
model, in a context that never saw the author's reasoning. So:

- the WORKER (author) keeps ONE thread per piece: `work -> rework -> rework ...` resume the same thread.
- the REVIEWER keeps ONE thread per piece: `review -> re-review ...` resume the same thread (still a
  separate session on a different model that never saw the author's thread - independence intact).
- the orchestrator holds, per piece, `{worker, reviewer}` resume handles and NEVER crosses them. A
  single thread doing implement->review->fix->re-review would collapse independence and is forbidden.

The committed fragment still records `reviewer_id != author_id` (the fidelity AUDIT, check-trace-evidence);
the resume handles are OPERATIONAL, not fidelity evidence.

## The handle MUST be the opencode session id, never a composed name

There are two identifiers and they must not be confused:

- The opencode SESSION/TASK id, e.g. `ses_11131a681ffeKnDQgUcHvTKiHK` - UNIQUE per dispatch.
- A composed/display NAME, e.g. `kha-worker-<model>-<unit>-<date>` - COLLIDES for split work (two
  sub-pieces of one unit on the same day share the name). Keying on this would CROSS threads.

Rule: the resume handle stored and used is ALWAYS the `ses_` session id captured from the Task result.
A composed name is at most a non-key label. `thread_ledger.py` REFUSES to store any handle that is not
a `ses_` id, and refuses to record one id under two `(piece, role)` keys.

## Probe evidence (run 2026-06 against the live Task primitive)

1. **Surfaced + resumable.** 4 concurrent subagents each stored a secret; the Task result surfaced a
   `ses_` id for each; resuming by that id (neutral prompt, no hint) recalled the OWN secret. Continuity
   is real, not prompt leakage.
2. **No collision at source.** All concurrent dispatches returned DISTINCT `ses_` ids.
3. **No cross-talk.** Each resume landed in its own thread (own secret), never another's.
4. **Identical NAMES still distinct ids.** Two workers with the SAME composed name
   (`kha-worker-...-module_b-20260622`, "split part 1/2") got distinct `ses_` ids
   (`ses_1112ea9b4...` vs `ses_1112ea481...`) and resumed to their OWN part. The name collides; the id
   does not. This is exactly the split-work hazard - the id is safe, the name is not.
5. **Bogus/expired id = graceful fresh.** Resuming a non-existent id did NOT error - it created a FRESH
   session ("NO-PRIOR-CONTEXT"), a NEW id. So a wrong/stale handle degrades to fresh and NEVER lands in
   another existing thread. The only cross-contamination path left is OUR bookkeeping reusing a real id
   for the wrong role/piece - which `thread_ledger.py --check` guards.

## Storage

Per-piece LOCAL claim `port/claims/<id>.yaml` (operational, gitignored, retired with the claim when the
piece integrates), under `threads: {worker: <ses_id>, reviewer: <ses_id>}`. Not committed; not fidelity
evidence.

## Fallback (always graceful, never a halt)

`resume` prints the `ses_` id on exit 0; on ANY non-zero it dispatches FRESH with a brief (the worker
re-reads its worktree; the reviewer re-reviews the proof commit). Non-zero covers: exit 3 (none recorded
/ stale), and exit 1 (`resume` REFUSED - it validates the whole claims dir at the point of use and never
hands back a cross-(piece,role)-reused or non-ses handle, so a worker's thread can never be resumed as
the reviewer's even if `--check` was not run separately). "Couldn't get / stale / refused" is a fresh
dispatch, never a stop and never a silent skip of the work.
