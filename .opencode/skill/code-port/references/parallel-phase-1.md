# Parallel Phase 1 (building the tooling with many explorations)

Phase 1 builds the comparison infrastructure - the differential harness, the gates, the
conformance checks, the dependency-map extractor, the six diff-tool classes - before any
translation. At scale that build itself parallelizes, on the WS-E0 coordination
substrate (`references/team-coordination.md`). The difference from parallel Phase 2: the
unit is a **tooling component**, not a translated module; acceptance is **broader than a
single seeded proof**, because every later wave *trusts* this tooling; and the work lands
in the **workbench**, not the product (tools live in the workbench).

Read with `references/differential-tooling.md` (the six tool classes + design rules),
`references/validation-ladder.md` (tiers), and `references/team-coordination.md` (the
claims/fragments/integrator substrate this reuses).

**Auto-mode (optional).** `tools/coordination/phase1_drive.py` is the read-only, deterministic
planner that turns this protocol into a per-unit next-action plan, reading `port/phase1-plan.yaml`
(scaffold with `tools/coordination/scaffold_phase1_plan.py`; template
`assets/phase1-plan.template.yaml`) - the F0/F1/F2/F3 rules below, machine-enforced and
fail-closed. `/port-autodrive` runs it at the charter's autonomy level; the same
`check-autodrive-integrity` gate and autodrive ledger apply, and it recommends only - the
orchestrator executes. See `references/auto-mode.md` ("Phase 1: the tool-build driver").

**Shard-and-generate the plan when authoring it in parallel.** A single `port/phase1-plan.yaml`
is one central registry: parallel sibling branches that each gate a different unit edit
near-identical, abutting stanzas, and git's 3-way merge corrupts it with NO conflict signal (a
rebase drops a "patch already upstream" hunk; a plain merge silently picks one side) - the same
shared-registry hazard `references/team-coordination.md` solves for TRACE. Apply the same fix here:
each unit's stanza lives in its own `port/phase1/units/<id>.yaml` fragment (template
`assets/phase1-unit-fragment.template.yaml`), the plan-wide scalars + unit ordering live in
`port/phase1/_meta.yaml` (template `assets/phase1-meta.template.yaml`), and the canonical
`port/phase1-plan.yaml` is GENERATED by `tools/coordination/generate_phase1_plan.py`, never
hand-merged. `phase1_drive.py` reads the generated plan unchanged. A CI drift check
(`tools/conformance/check-phase1-plan.sh`) fails if the committed plan disagrees with the
fragments, and skips until `port/phase1/units/` exists - so a small or serial Phase 1 may keep
the monolithic scaffolded plan and adopt fragments only when it fans out.

## F0. Prerequisite: a signed Phase 0

Do not fan out until Phase 0 is human-signed: the SOURCE is imported at a pinned commit,
the configuration is pinned, the live-subset method is fixed, and the canonical reference
run is defined and archived (`reference/runs.md`). The dependency-map extractor (F2/F4)
depends on that live-subset and configuration evidence; a fan-out over an unsigned Phase
0 builds tooling against a moving target.

## F1. Layer 0 (near-serial): the differential harness first

Everything else compares *through* the differential harness against the reference run,
so it comes first and nearly serial - one small, owned surface. Until Layer 0 is gated,
the Layer-1 fan-out has nothing to validate against. Gate Layer 0 before opening the pool.

### Layer-0 acceptance (non-circular)

Layer 0 cannot validate itself *through* the harness, so it is accepted on its own
terms: the SOURCE build with instrumentation off reproduces the canonical reference
outputs byte-for-byte (the results-inertness guarantee in `differential-tooling.md`);
dump/restore (or parse/compare) fixtures round-trip; two identical SOURCE dumps compare
green; seeded corruption of a dumped value / tag / record order / count goes red then
green; the harness's dump-format and comparison contract gets an independent review; and
its enforcement-table row + evidence are recorded. Only then is Layer 0 gated and the
Layer-1 pool opened.

## F2. Layer 1 (fan out in parallel)

Once Layer 0 is gated, the rest is largely independent and **fans out exactly like parallel Phase 2**:
the orchestrator launches the WHOLE Layer-1 ready-set (every unit whose `depends_on` + Layer 0 are
integrated - the ladder gates, the conformance checks, the dependency-map extractor, the six diff-tool
classes) as parallel worker subtasks at once, then their independent reviews, never one at a time. This
reuses the WS-E0 substrate unchanged - atomic claims, ephemeral `.worktrees/`,
per-component PRs, independent review, the integrator queue - with one placement
difference: **the integrator merges tooling into the workbench** (the product is not
involved in Phase 1), then RELEASES the component's now-done claim (`tools/coordination/release_claim.sh`)
so a completed tooling claim cannot linger into Phase 2. Tooling components are themselves owned surfaces or leaves: a
shared harness API is owned (versioned contract); an independent conformance check is a
leaf.

Tool contracts follow **producer-before-consumer** (`references/team-coordination.md`):
a component declares the contracts it provides and consumes; a consumer may develop
against a *draft* producer contract but is not accepted - nor usable as evidence by any
wave - until that producer contract is itself F3-accepted, and a later producer-contract
change marks its consumers stale (rebase + re-accept).

## F3. Acceptance per component is broader than a seed

A seeded red->green proof is necessary but **not sufficient** for tooling, because later
waves rely on it. Each Layer-1 component is accepted only with ALL of:

1. a current **seeded red->green** evidence record (via `/port-seed`), linked from the
   enforcement row - the detector fires; methodology conformance checks additionally keep
   a compact record under `tools/conformance/seeded-bugs/`;
2. a **source-side demonstration run** - it behaves correctly on the real SOURCE, not
   only on a fixture;
3. **inertness / non-vacuity** evidence - a diff/probe tool is byte-inert when off (the
   results-inertness guarantee in `differential-tooling.md`); a check is non-vacuous: it
   exercises its enumerated target set (at least one in-scope file/routine/path/record
   where a hit is expected), fails closed on a missing scan root, and handles "not
   applicable" explicitly rather than reporting a silent green on an empty scan;
4. an **independent review of the tool itself** (separate session/person from its author);
5. its **`tools/README.md` enforcement-table row** updated to ENFORCED in the same change.

Until a component meets all five, downstream waves must not depend on it.

## F4. Parallel read-only exploration feeds the map

Use read-only `explore`-style agents in parallel for the analysis-heavy parts -
live-subset determination and call-graph / coupling analysis - that do not mutate state
and so need no claim. Their output is the **confidence-labeled dependency map** (edges
proven / suspected / unknown; unknown stays guarded, out of the leaf pool) and the
**parallelizability + owned-surface assessment** that parallel Phase 2 consumes
(`references/team-coordination.md`: the topology is a hypothesis to test, not assume).

## Done-when

Layer 0 is gated; each Layer-1 component meets the F3 acceptance and is merged into the
workbench in parallel; and the confidence-labeled dependency map and the
parallelizability assessment exist and are human-reviewed - ready for Phase 2.

> Execution note: this is a protocol for a live, multi-contributor Phase 1; it runs on a
> real signed Phase 0 with the WS-E0 operational machinery (generator, dashboard,
> integrator) in place. The methodology (this protocol + the substrate + the per-tool
> acceptance ladder) lands on the branch; the run itself is per-project.
