# Seeded-bug record - `check-trace-evidence.sh`

A detector is trusted only once it has been SEEN to fail. This is the red-then-green
demonstration for `tools/conformance/check-trace-evidence.sh`, using a defect representative of
the class it targets - a proven TRACE entry whose evidence does not exist - rather than a syntax
error.

## The failure class

`check-trace-evidence.sh` is the check that makes `status: proven` MEAN something: it refuses a
TRACE entry that claims a proof tier while citing a proof report or review report that is absent
from `docs/evidence/`. Without it, an entry can be marked proven by editing one word, and nothing
in the repository objects.

That is precisely the claim on which every later acceptance rests, so the check failing OPEN is
worse than the check not existing - it manufactures confidence rather than withholding it.

## The defect this record documents (why the check is being changed)

The scanner keyed entry starts on a single hard-coded spelling:

```awk
infiles && /^  - source:/ {        # two-space indent, `source` as the FIRST key
```

A TRACE generated by a YAML emitter does not look like that. `yaml.safe_dump` writes list items
at column 0 and orders keys as the mapping was built, so real entries begin:

```yaml
files:
- id: 0001
  source: src/example/thing.F90
  status: proven
```

Neither the indent nor the first key matches, so the scanner matched ZERO entries on a TRACE with
several hundred of them. It then took the `[ -z "$records" ]` branch and reported

```
check-trace-evidence: no file entries in port/TRACE.yaml; nothing to check (skipping).
```

and exited 0 - GREEN, inside an all-green conformance run. The check had never, in the life of
the repository that found this, verified a single entry. Both spellings are the same YAML
document; only the scanner distinguished them.

This is the harder half of the class: not a check that is missing, but a check that is PRESENT,
GREEN, and vacuous - and whose greenness is read as evidence.

## The fix

Two independent changes, either of which alone would have prevented the silent pass:

1. **Parse the document, not one rendering of it.** An entry now starts at any list item under
   `files:` at any indent, whatever its first key (`/^[ \t]*-[ \t]*[A-Za-z_]+:/`), and fields are
   matched by KEY rather than by indent-qualified pattern. A `files:` block ends where the next
   top-level key begins.

2. **Fail closed when the TRACE cannot be read.** Parsing zero records from a file that plainly
   contains a non-empty `files:` block is not "nothing to check" - it is "I could not read this."
   That now exits 2 as UNRELIABLE with a message naming the cause. "Nothing to check" is reserved
   for a TRACE that genuinely has no entries.

The second is the durable half. A future TRACE layout this scanner does not anticipate will now
stop the run instead of quietly skipping forever.

## Demonstration

Run against a real generated TRACE (several hundred entries, none proven):

| | before | after |
|---|---|---|
| entries parsed | 0 | all |
| verdict | `nothing to check (skipping)`, exit 0 | `0 proven, 0 violations`, GREEN |

Then seed the representative defect - mark one entry `status: proven`, cite a `proof:` report that
does not exist, and leave `review:` null:

| | before | after |
|---|---|---|
| verdict | `nothing to check (skipping)` | `1 proven, 3 integrity violation(s)` |
| exit code | 0 (GREEN) | 1 (RED) |

Before the fix the seeded defect is invisible: the check reports the same skip whether the TRACE
is honest, corrupt, or fabricated. After it, the entry is read, the missing proof report and the
null review are both named, and the run fails.

## Standing rule this reinforces

A check that reports "nothing to check" must prove there was nothing to check. Any scanner whose
input is a structured document should treat "I parsed zero records from a non-empty file" as
UNRELIABLE, never as success - the three-state contract (verified / verified-not /
could-not-determine) applies to the parse itself, not only to the property being checked.
