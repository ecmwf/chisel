# tools/

All instrumentation, proofs, and automation. Design rules (full detail in the skill's
`references/differential-tooling.md`):

- Every diff/probe tool sits behind a switch so it is inert when off (prefer a compile-time switch over a runtime
  env var). The inertness guarantee is on RESULTS: with it off, the build reproduces the reference
  run's outputs byte-for-byte - not a hash-identical binary.
- Dump formats are raw and exactly specified (endianness, record layout, step/substep/location/field
  tags), and read back exactly by the other side.
- One small module per tool; resist merging them. Proofs have exit-code semantics, are CI-callable,
  and land evidence in `docs/evidence/`.
- Run the conformance suite with `bash tools/run-conformance.sh` (parallel; prints a per-check verdict
  summary + the output of any non-green check; exits non-zero if any check is not green). It globs
  `conformance/` and `conformance/project/`, so it never goes stale - never hand-list scripts. The
  serial fallback is the same runner with one job, `CONFORMANCE_JOBS=1 bash tools/run-conformance.sh`;
  a hand-written loop over `tools/conformance/*.sh` is not equivalent (it misses the project checks
  and the runner's single product-root resolution).
- The tool tests: `bash tools/tests/run.sh` runs every registered test, or the ones named on its
  command line. CI runs only the tests a change can affect: `tests/select_tests.py` reads
  `tests/covers.json`, the files each test reads, measured by `tests/trace-covers.py` (it runs every
  test under strace). After adding a test (register it in `run.sh`) or changing what one reads,
  regenerate the map with `python3 tools/tests/trace-covers.py`; until then a test the map does not
  know runs on every change. CI installs the analysis toolchain (clang, gfortran, libclang, fparser) only when
  a selected test or the port's own checks need it.
- `coordination/yaml_get.py FILE KEY.PATH` (or `--list`) reads one YAML value for a shell tool,
  through the strict loader the Python tools share, so both read the same data (an alias is its
  value, a nested key is not a top-level one, a repeated key is an error). Exit 0 prints the value,
  3 means absent or null, 2 means it cannot answer - the caller reports UNRELIABLE or refuses,
  never falls back to a default. The contract is in the script's header.

| Dir | Contents |
|---|---|
| `diff/` | The six differential tool classes (staged reference dump, identical-input/replay operator diff, range probes, boundary/communication probe, subsystem disable-switches, executable contracts) plus the poison-discriminator helper. |
| `proofs/` | Validation-ladder tiers (R0-R5) as scripts, one per tier/kernel-group. |
| `conformance/` | One `check-*.sh` per convention/trust property - exit-code-clean, CI-callable, each backed by a seeded red→green record in `seeded-bugs/`. The full list and enforcement status is the honesty table below. Base-shipped checks here are methodology; a port's OWN program-specific checks (and their seeded-bug records) go under `conformance/project/`, carved out as project-layer (`merge=ours`) in `.gitattributes`. |
| `build-checks/` | Generic checks on a fresh TARGET build, read from the build's own compilation database (`compile_commands.json`): the build contract on the flags each translation unit received and the fused multiply-adds in its object (`check-build-flags.py`), the tests on a sanitizer build (`check-sanitized.py`), one type per external name and no caller-local prototype (`check-prototypes.py`). They need a build, so a port's proof script runs them after building unconditionally (`references/langs/c.md`, "Build checks"); seeded red→green records in `conformance/seeded-bugs/build-*.md`. |
| `coordination/` | The generic (methodology-layer) framework for a parallel, many-contributor port: the deterministic TRACE generator, the SOURCE dependency-map extractor, the claim / interface-contract checkers, the read-only dashboard, the auto-mode planners (Phase-2 translation + Phase-1 tool-build), the sign-off-guarded finalize (auto-land: tag/land/push/teardown), the worker-worktree provisioner (isolated workbench + product worktrees per piece before dispatch, serialized; its teardown refuses, removing nothing, while the piece's workbench evidence is not yet gathered onto the workbench mainline), the sanctioned contribute push (auto-opens a methodology-layer-only PR to the base for `/port-contribute-to-base`; never merges), the Phase-1 plan scaffolder (writes the canonical representative tool-build plan so auto-mode has a Layer-0-first Phase 1 to drive instead of dead-ending on an absent plan), the Phase-1 plan generator (`generate_phase1_plan.py`: assembles the canonical `port/phase1-plan.yaml` from per-unit `port/phase1/units/*.yaml` fragments + `_meta.yaml` so parallel authors never hand-merge the one central plan, exactly as TRACE is generated from status fragments), and the sanctioned sync-resolution merge (the layer-driver base→instance merge into the ephemeral `sync/<id>` branch, shape-checked never to touch `main`), and the sanctioned claim-release (`release_claim.sh`: a fail-closed guarded `push --delete` of an integrated, unbound Phase-1 tooling claim's ref plus its `port/claims/` file, so a completed claim never lingers into a later phase's planner), and the worker-isolation preflight (`assert_isolated.sh`: a Kha-Worker's fail-closed first check that it is confined to its own provisioned `.worktrees/<id>` worktree on `work/<id>` and an isolated product worktree - it DERIVES the canonical roots from `<id>` and the layout when they are not in the env, since a dispatched subagent does not inherit the orchestrator's shell env, and `--export` re-emits the verified roots for the worker to `eval`, refusing to edit or commit in the shared tree if it was dispatched unprovisioned), and the sanctioned integration auto-land (`integrate_land.sh`: a guarded fast-forward merge of a Phase-1 workbench piece the deterministic planner reports integration-ready - conformance green, clean FF, and a clean review by a distinct reviewer (on a different model by dispatch convention) bound to the proven commit by check-trace-evidence - so it lands integration with no manual git), and its Phase-2 analogue (`integrate_product.sh`: the guarded SQUASH land of a planner-ready, reviewed piece onto the separate PRODUCT mainline - two-root conformance at HEAD and on the merge result, stale-base rejection, roll-back-on-red, then pushes the product, so the target repo fills one reviewed piece at a time). Each checker `.py` is wrapped by a `conformance/check-*.sh`; the per-project fragments and DAG data it reads live under `port/` and `scoping/`. |
| `scoping/` | Per-project live-subset and dependency/call-graph extraction (porting order, workstream partitioning), plus `port-progress.py` - a read-only progress view derived from TRACE, wired into `/port-sprint-start`. |

Naming: proof scripts are `proofs/ci-<tier>-<subject>.sh` (CI-runnable, fast) or
`proofs/manual-<tier>-<subject>.sh` (compute-system); diff tools live one per dir as `diff/<tool-id>/`.
Mechanical mass-transforms (charter §5) also live here as reviewed, committed scripts.

## Enforcement status (honesty table - keep current)

Documentation must never imply a check exists before it does. Each ENFORCED check below is CI-run and
has a seeded red→green record in `seeded-bugs/` (what it catches lives there). Until a row says
ENFORCED, agents check that property by hand and must not rely on CI; move a row up only in the same
commit that lands its script.

| Product README stays product-focused | ENFORCED - `conformance/check-product-readme.sh` |

Not judged - UNRELIABLE, never a pass: a TARGET name the naming map does not give, until `anchors.yaml` `names` lists it; a constant of an interface body, of an internal procedure or declared inside a BLOCK construct, or one depending on an argument of its procedure; a TARGET constant a function computes from its parameters, for a SOURCE compile-time constant; a constant of a Fortran INCLUDE file no SOURCE file INCLUDEs; a CHARACTER constant or string; a TARGET header no TARGET file includes that is not self-contained (it is parsed on its own).
